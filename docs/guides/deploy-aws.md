# Deploy to AWS

DBPilot's Terraform is complete and validated for three environments, but per this
program's standing rule, nothing is ever applied to a real AWS account by the project
itself: `aws-dev` and `aws-prod` are validated, linted and security-scanned, and exercised
end to end against a throwaway Floci emulator (`make tf-aws-on-floci`), so the IaC is
proven deployable without ever touching a real account in this repository's own
verification. Deploying for real is something you choose to do with your own AWS account
and credentials.

## Environments

| Env | Purpose |
| --- | --- |
| `local-floci` | Applied automatically by `make up`, against the local Floci emulator. Not a deployment target, it is how the local stack proves its own Terraform, with `storage=s3` and `key_mode=kms` exercised for real against the emulator. |
| `aws-dev` | A full, cheaper copy of production: fewer AZs, smaller instance sizes, no deletion protection. |
| `aws-prod` | Multi-AZ, deletion protection on, larger ceilings. |

Modules (`infra/terraform/modules/`): `network`, `database` (RDS PostgreSQL), `cache`
(ElastiCache), `storage` (S3), `kms`, `secrets` (Secrets Manager), `ecr`, `service` (ECS
Fargate behind an ALB), `observability` (CloudWatch). There is deliberately no `email`
module and no queue/event module: DBPilot's backend has no mail code path and its one
background process (the scheduled-backup worker) polls Postgres directly, never a queue.
See [ADR-0004](../architecture/adr/0004-no-queue-or-mail-module.md).

## Key mode and storage in this release

Unlike a sealing backend that is provisioned but not implemented, DBPilot's `kms` key mode
and `s3` storage backend are both real, working code paths (`core/sealing.py`'s `KmsSealer`,
`core/storage.py`'s `S3Storage`), exercised by `make test-matrix` against Floci and by
every e2e/QA run against the real local-floci environment. `aws-dev/main.tf` and
`aws-prod/main.tf` both set `KEY_MODE=kms` and `STORAGE=s3` in the ECS task environment,
the production-correct values the boot guard itself requires (`STORAGE=local` is refused
in production). `LOCAL_MASTER_KEY` and `SESSION_SECRET` are still generated by
`module.secrets` and delivered through Secrets Manager even in `kms` mode, since
`SESSION_SECRET` always signs sessions regardless of the sealing backend.

## Prerequisites to deploy for real

- An AWS account and credentials with permission to create the resources above.
- `terraform.tfvars` for the environment you are targeting, copied from
  `terraform.tfvars.example` and filled in.

## Validate without touching AWS

```sh
make tf-validate     # terraform validate, every environment (no backend, no credentials)
make tf-lint         # tflint, every module and environment
make tf-security     # checkov; every skip carries its reason inline
make tf-aws-on-floci  # full aws-dev apply, re-plan, destroy against a throwaway Floci
```

`tf-aws-on-floci` is the one that actually exercises `terraform apply`, a second `plan`
that must show zero adds or replacements, and `terraform destroy`, all against an
emulator, so plan-time bugs that `validate` alone would miss are caught before a real
account ever sees this configuration.

## Deploying for real (your account, your choice)

```sh
cd infra/terraform/envs/aws-dev
cp terraform.tfvars.example terraform.tfvars   # edit: region, instance sizes
terraform init
terraform plan
terraform apply
```

Then build and push the server and web images to the ECR repositories Terraform created,
run `dbpilot migrate` as a one-off ECS task, and `dbpilot create-admin` to create the first
organization owner. Repeat against `aws-prod` with its own `terraform.tfvars` when ready;
it has deletion protection on by default, review every `var.*` before applying.

## What AWS mode turns on in the app

| Setting | `aws-dev`/`aws-prod` value | 0.1.0 behavior |
| --- | --- | --- |
| `KEY_MODE=kms`, `KMS_KEY_ID=<module.kms alias>` | set | Real: connection secrets and the AI provider key are sealed with AWS KMS Encrypt/Decrypt |
| `STORAGE=s3` | set | Real: backup dumps and uploaded SQLite files go to S3, never local disk, so the worker and the API share them regardless of which replica wrote one |
| `COOKIE_SECURE=true`, `CORS_ORIGINS=<hostname>` | set | Real: required by the production boot guard |
| `DATABASE_URL`, `REDIS_URL`, `SESSION_SECRET`, `LOCAL_MASTER_KEY` | set | Real: delivered through the ECS task definition's Secrets Manager references (`module.secrets`) |

See [local-with-aws.md](local-with-aws.md) for the equivalent picture against the local
Floci emulator, and [security.md](../architecture/security.md) for the production boot
guard's full rules.
